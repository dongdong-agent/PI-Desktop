# PI Agent · 需求一页纸（轻量版，非完整 PRD）

> ⚡ 产品名定稿（2026-08-18）：**PI Agent**（原名 AI 工作台，东哥更名）
>
> 版本：v0.2 · 定稿人：东哥 / 小羽 · 2026-08-18
> 定位：给「日常 Agent 工作」用的个人 AI 桌面应用。**MVP 只实现等价于 PI 终端的能力，但架构上为全面扩展设计好接口。**

---

## 1. 一句话定位

一个围绕「AI 编程 + 对话 + 创作 + 能力扩展」的个人桌面工作台：一个能装技能、能换皮肤、能带桌面宠物的 Agent 中枢。

## 2. 核心用户

东哥本人（独立开发者，重度使用 AI Agent 工作）。无团队、无多角色对齐需求。

## 3. 核心功能清单（MVP，P0）

> 以「等价 PI 终端」为准，先跑通最小可用闭环：

- [ ] **对话/编码控制台**：多轮对话、流式输出、代码块高亮与复制
- [ ] **会话管理**：多会话、长对话持久化与恢复（对应“长对话稳定性”）
- [ ] **模型/Agent 接入**：可切换模型提供方（对接后端 API，可扩展）
- [ ] **系统提示词 / 上下文注入**：可编辑系统 prompt
- [ ] **基础设置**：主题、字体、API 配置
- [ ] **进/出网页版**：同一套前端可部署为 Web

## 4. 扩展能力（远期，P1+）

> MVP **不做**，但架构必须给这些留好扩展点（见第 6 节）：

- 文档 / PPT / 网页 / 图片 / 视频 生成
- AI 调研分析
- 技能系统（不断增加的 skills）
- 提示词库、素材库
- 皮肤 / 主题更换
- 桌面宠物
- 各种增强 Agent 能力（含外部 Agent 协同）

## 5. 非目标 / 不做（显式边界）

- 不追求极致性能与最小包体积（小应用，够用即可）
- 不依赖多人协作流程（无 code review 流程需求）
- 桌面宠物、素材库等**不进入 MVP**，仅预留接口

## 6. 核心架构原则：可扩展接口（贯穿一切的底座）

> 为什么重要：功能会不断长出来（技能、能力、皮肤、宠物、Agent…），
> 所以 **MVP 的价值不只是能聊，而是把「注册-扩展」的骨架打对**。

| 扩展点 | 接口/契约 | 说明 |
|---|---|---|
| **能力注册中心** | `Capability` 统一接口 | 每一类能力（对话/编码/文档/图片…）都是注册进中枢的一个插件，对外暴露统一生命周期与调用协议 |
| **模型/Agent 提供方** | `Provider` 接口 | 可插拔接入不同后端（火山 ARK、本地模型、外部 Agent 网关） |
| **技能系统** | `Skill` 接口 | 对应「不断增加的技能」，统一清单、匹配与调用机制 |
| **提示词库 / 素材库** | 结构化数据模型 + 查询接口 | 内容资产与核心逻辑解耦，可检索、可扩展 |
| **皮肤/主题** | 主题 token 体系 | 界面样式与业务解耦，可换肤 |
| **桌面宠物** | 独立窗口模块 + 事件接口 | 独立于主窗口的生命周期，MVP 只留占位 |
| **会话层** | 持久化 + 恢复契约 | 长对话稳定性的地基，MVP 就要做对 |

**核心心智模型**：`中枢(Hub) + 插件(插件/能力/技能) + 注册表(Registry)`。
MVP 只实现「中枢 + 对话/编码这一个 Capability + 会话层」，但 Hub/Registry/接口契约从第一天就按上述形态搭建，后续能力=往注册表里加实现，不返工改骨架。

## 7. 技术栈（已定稿）

**React + TypeScript + Vite + Tauri**
- 一套前端 → Windows 桌面（Tauri）／未来 Mac/Linux／网页版（Vite 部署）
- 纯 AI 开发：AI 对 React+TS 生成质量最高，翻车率最低
- 长对话稳定：虚拟化 + 流式增量 + 类型化状态层 + 订阅清理规范

## 8. 里程碑（建议顺序）

1. **M0 骨架**：Vite(React+TS) + Tauri，跑通窗口 + 打包 exe 最小闭环 ✅ 已完成
2. **M1 中枢骨架**：Hub + Registry + 会话层 + 对话/编码 Capability（≈ PI 终端能力）✅ 已完成
3. **M2 打磨**：长对话稳定、流式、主题 token、网页版可部署
4. **M3+ 扩展**：按优先级长技能/能力/皮肤/宠物等

落地「中枢 + 插件 + 注册表」架构：

| 模块 | 文件 | 职责 |
|---|---|---|
| 类型契约 | src/core/types.ts | Capability / Provider / Hub / 事件 全部接口 |
| 事件总线 | src/core/events.ts | 零依赖类型安全事件总线 |
| 注册表 | src/core/registry.ts | 插件注册（可监听变化） |
| 中枢 | src/core/hub.ts | 编排 + 统一调用入口 hub.call(cap, action, payload) |
| 状态层 | src/core/store.ts | zustand 单一数据源 + localStorage 持久化 |
| 绑定层 | src/core/bind.ts | 事件→状态投影（写入路径唯一） |
| 引导 | src/app/bootstrap.ts | 创建唯一 Hub、注册内建插件、恢复状态 |
| 对话能力 | src/capabilities/chat.ts | 第一个插件：send/stop 两动作 |
| Provider×2 | src/providers/ | echo(本地测试) + openai-compat(远程，兼容火山方舟) |
| UI | src/ui/ | 侧栏 / 聊天视图(虚拟化) / 消息渲染 / Provider 面板 |

核心链路：`UI → hub.call("chat","send") → Capability → Provider.streamChat → 事件总线 → 绑定层 → store → UI`

测试：`npx vitest run`，4/4 通过（含中止场景）

> ⚠️ 方向修正（2026-08-18）：M1 早期把「对话能力」做成了**自研聊天 + 自接模型 API**（echo / openai-compat）——
> 本质是另起炉灶复刻 PI 的功能。东哥明确指出：**要的是 PI 的桌面客户端，底层必须是真 PI 终端能实现的所有能力**。
> 遂转向：以官方 SDK（`@earendil-works/pi-coding-agent`，内置 createAgentSession/SessionManager/RPC）驱动真实 PI。
> 若干部件（Hub/Registry/主题/UI 外壳）保留并复用；自研 chat Capability 与 Provider 不再作为主链路。

### M2（进行中）：真实 PI 驱动 ✅ 核心链路已验证

**架构定稿：Node sidecar 内嵌真实 PI SDK（方案 A，官方推荐 embed 路径）**

```
WebView UI ──Tauri IPC──▶ Rust PiBridge ──spawn/stdio──▶ Node sidecar ──▶ 真实 PI AgentSession
      ◀── pi_event 事件流 ◀────────────────┘   ◀── JSONL 指令 ─┘     │ 复用 ~/.pi/agent 全部配置
                                                    （prompt/steer/abort/new_session/get_state…）
```

| 模块 | 文件 | 职责 |
|---|---|---|
| Sidecar 协议层 | drivers/sidecar/sidecar.mjs | JSONL 指令→ AgentSession 调用；事件转发 stdout |
| Tauri 桥 | src-tauri/src/pi_bridge.rs | spawn sidecar、stdin 写入、stdout 逐行 emit `pi_event`；启动即 init |
| 前端桥 | src/pi/bridge.ts | invoke 发送指令 + request/response 关联 + 事件分发（幂等单例） |
| 事件模型 | src/pi/eventModel.ts | 真实 AgentSession 事件 → 可渲染视图模型（text/thinking/toolCall/toolResult） |
| 主界面 | src/ui/PiChatView.tsx | 会话历史恢复 + 流式渲染 + 工具卡片 + 输入/停止 |
